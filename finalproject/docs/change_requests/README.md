# 개발 단위 간 수정 요청

상태: 공용 개발 절차 · 상위 규칙: [AGENTS.md](../../AGENTS.md)

## 1. 요청이 필요한 경우

- 현재 담당 이외의 개발 단위 코드를 수정해야 한다.
- TBD가 결정되었고 해당 인터페이스를 다른 개발 단위도 사용한다.
- 기존 공용 메시지·토픽·enum·QoS·시간 정책·ID·종단 동작을 변경한다.

개발 단위는 AMR(PC 1·2), 관제(PC 3), 비전(PC 4)다. AMR 요청에는 필요하면 robot1·robot6 적용 상태를 구분한다. 요청서 작성은 상대 코드 변경 권한이나 구현 승인을 의미하지 않는다.

미결 TBD가 있다는 이유만으로 모든 항목의 요청서를 미리 만들지 않는다. 해당 문서에서 논의하고, 구체적인 변경안 또는 결정이 생기면 요청서를 생성한다. 공유 계약에 대해 상대 변경이 필요 없다고 판단한 경우에도 확인 근거를 기록한다.

## 2. 파일명과 상태

실제 요청부터 `CR-NNN_MM-DD_HH-mm_<짧은_제목>.md` 형식으로 순번과 **최초 작성 시각**을 반드시 포함한다. 이 README는 양식이며 아직 발행된 수정 요청은 없다.

- 시각은 한국 표준시(KST, UTC+09:00), 24시간제로 기록한다. 월·일·시·분은 각각 두 자리다.
- 요청한 `mm/dd hh:mm`의 의미를 유지하되, Windows 파일명에서 사용할 수 없는 `/`와 `:`를 대체하여 `MM-DD_HH-mm`으로 표기한다.
- 예: 9월 6일 14시 05분 작성 → `CR-001_09-06_14-05_토큰_계약_변경.md`.
- 본문 작성 시각은 `YYYY-MM-DD HH:mm KST`로 기록하여 연도를 구분한다.
- 후속 수정 시 최초 작성 시각과 파일명은 유지하고 변경 시각은 검토·결정 이력에 기록한다. 순번은 연도 변경 시에도 재사용하지 않는다.

권장 진행 상태는 초안 → 검토 중 → 합의 → 반영 중 → 반영 완료 → 통합 검증 완료다. 보류·철회 시 사유를 기록한다. 합의는 계약 합의이며, 코드 수정은 별도의 명시적 승인 범위를 확인한다.

전체 상태와 개발 단위별 적용 상태를 따로 기록한다. 담당자가 수정했다고 보고한 사실과 통합시험으로 확인한 사실을 구분한다.

## 4. 완료 기준

기준 기능·인터페이스 문서가 갱신되고, 영향받는 모든 단위가 반영 또는 변경 불필요를 확인하고, 관련 통합시험 결과가 기록되면 완료 처리한다. 시험이 미실행이면 '통합 검증 완료'로 표시하지 않는다. 해결한 TBD ID는 이 요청서를 링크하고 재사용하지 않는다.
