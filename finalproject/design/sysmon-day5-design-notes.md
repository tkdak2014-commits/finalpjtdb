자료의 Captured/Following 및 차량 추적은 교육 예시다. 우리 프로젝트에서는 누수·고임, 적치물, 조명 이상, 시설 손상 후보와 순찰 상태로 치환한다. PDF만으로 특정 협업 시나리오나 순찰 실행 버튼이 필수라고 단정하지 않는다.

사용자가 별도로 전달한 “빈 데이터셋 → 빈 이벤트 DB에 content 입력 → 웹 반영”과 로그인 등 동작 영상 촬영 조건도 반영했다. ‘빈 DB’는 이벤트 0건인 시연 DB를 뜻하며 관리자 계정은 사전 준비한다. 서버 시작 때마다 기존 DB를 지우지 않는다.

## draw.io 읽는 순서

1. **01 전체 구조**: 외부 감지·AMR 데이터가 Sysmon 수신부, Flask, SQLite를 거쳐 웹으로 전달되는 큰 그림.
2. **02 로그인 및 화면 흐름**: 관리자가 로그인해 영상·상태를 확인하고 이력을 검색하는 과정.
3. **03 초기화 및 데이터 처리**: 빈 상태 준비, 영상·상태·이벤트 수신, 검증, 저장, 화면 갱신 반복.
4. **04 UI 목업**: 이전 화면 초안을 함께 수록. 로봇별 상태로 보완했으며 카메라 소스 배치는 협의 필요.
5. **05 DB 구조**: users, robot_status, events 초안. 상태 테이블의 위치 좌표 및 임무 식별자는 실제 수신 메시지에 맞춰 추가한다.

타원은 시작·종료, 사각형은 처리, 마름모는 조건 분기, 원통은 DB다. 화살표는 처리 순서 또는 전달 데이터를 뜻한다. 전체 구조는 데이터 관계도이고, 02·03은 실행 순서를 보여주는 플로우차트다.

## 가장 중요한 동작 원칙

- 사용자 로그인과 데이터 수신은 독립적으로 진행한다. 로그아웃해도 서버는 이벤트를 저장한다.
- 웹페이지는 Flask 서버를 통해 DB에 접근한다. 상태·이벤트 API도 세션 인증을 확인한다.
- 영상은 실시간으로 전달하고, 감지 근거 이미지와 메타데이터를 이벤트로 저장한다.
- 이벤트가 없을 때와 로봇 연결이 끊겼을 때는 서로 다른 상태로 표시한다.
- 순찰 명령 생성·실행은 이번 Sysmon 흐름에 포함하지 않는다. Sysmon은 로봇별 순찰·협업 상태를 받아 표시한다.
- 중복 제거, 데이터 검증, 저장 실패 재시도는 안정성을 위한 설계 제안이다. 재시도는 수신부를 막지 않는 별도 대기열로 처리하고, 횟수·간격·보존 방식을 구현 단계에서 정한다.
- 관리자 확인 처리는 선택 기능이다. PDF에서 이를 필수 기능으로 특정하지 않았다.

## 시연 및 통합 검증 순서

| 순서 | 조작 / 입력 | 화면 및 저장 확인 |
| --- | --- | --- |
| 1 | 이벤트 0건 DB로 서버 시작 | 계정 존재, 감지 이력 0건 |
| 2 | 잘못된 계정으로 로그인 | 오류 표시, 관제 접근 불가 |
| 3 | 정상 로그인 | 빈 이벤트 목록과 연결 대기 표시 |
| 4 | 로봇별 상태 및 영상 입력 | 영상 창과 해당 로봇의 상태 갱신 |
| 5 | 누수 의심 시연 이벤트 1건 입력 | SQLite 행 생성, 웹 목록·알림 표시 |
| 6 | 날짜·로봇·유형으로 검색, 행 선택 | 정확한 결과와 시간·위치·근거 이미지 표시 |
| 7 | 검색 결과가 없는 조건 입력 | 검색 결과 없음 표시 |
| 8 | 로그아웃 중 이벤트 추가 후 재로그인 | 미접속 중 저장된 이력도 조회 가능 |
| 9 | 중복 이벤트 / 영상 연결 단절 | 중복 행 없음 / 연결 끊김 표시 |

로봇 연동 전에는 시연 데이터를 사용하되 영상에 시연 데이터임을 명시한다. 테스트·통합 계획을 문서에 남기고, 최종 동작 영상은 실제 웹 구현 후 촬영한다.
